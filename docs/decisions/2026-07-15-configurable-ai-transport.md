# 使用可配置的第三方 AI 传输层

> 状态：已于 2026-07-20 被[微信云开发生产运行时决策](2026-07-20-cloudbase-production-runtime.md)取代；本文只保留早期本地验证背景。

日期：2026-07-15

状态：已采用

## 背景

第二切片需要验证“简历终结者”的真实文本诊断质量。模型由第三方 API 提供，同一服务可能根据模型类型使用 Responses 或 Chat Completions 协议，模型选择也会随成本调整。

## 决定

业务层只依赖统一的结构化评审接口；第三方地址、密钥、模型和协议分别通过 `AI_BASE_URL`、`AI_API_KEY`、`AI_MODEL` 和 `AI_PROTOCOL` 配置。

传输层提供 Responses 与 Chat Completions 两个适配器。当前本地配置启用 Responses，但业务代码不得根据模型名称猜测协议，也不在第二切片中实现自动价格路由或用户端模型选择。

所有模型输出必须经过统一的 JSON 结构、原文证据和安全校验。第一次输出不合规时重新生成一次，第二次仍失败则不展示报告。

## 理由

1. 用户可以根据成本手动更换模型和协议，而不修改小程序和诊断规则。
2. 严格 JSON Schema 降低第三方兼容接口返回格式漂移的风险。
3. 独立证据校验能够阻止模型把不存在的简历内容当作确定事实。
4. 单活动配置足以验证当前产品价值，避免过早建设复杂的多供应商路由系统。

## 替代方案

- 把模型和接口写死在业务代码中：实现更少，但更换模型会污染诊断与页面逻辑。
- 自动按价格或质量路由：长期可能有价值，但当前缺少稳定评测和真实成本数据。
- 直接把第三方响应展示给用户：无法保证结构、证据和安全边界。

## 影响

- 真实密钥只存在于被 Git 忽略的本地 `.env`。
- PDF 和 DOCX 原文件只在本地 API 内存中解析，不落盘，也不直接发送给模型。
- 提取出的简历正文和可选完整 JD 会发送给所配置的第三方服务，前端必须获得用户明确确认。
- 第二切片不在本服务持久化正文；任务完成或失败后从内存中移除。
- 更换模型时需要同时明确 `AI_PROTOCOL`，修改环境变量并重启服务。
