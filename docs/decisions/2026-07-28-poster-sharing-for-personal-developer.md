# 2026-07-28：个人开发者改用小程序码海报分享

## 背景

当前小程序主体为个人开发者，不能把微信好友与朋友圈原生分享作为稳定的产品入口。产品仍需要传播能力，并且首页比单个角色更适合第一次向新用户解释“这里有四位不同专业暴君”。

## 决定

1. 停用报告页的 `open-type="share"`、`onShareAppMessage` 和 `onShareTimeline`，不再维护朋友圈单页落地路由。
2. 首页提供四位公开暴君同框的总览海报，扫码进入首页；报告末尾提供当前暴君的单角色邀请海报，扫码进入对应角色详情页。
3. 小程序码由云函数通过 `cloud.openapi.wxacode.getUnlimited` 生成，服务端固定允许的页面和角色；前端只负责用 Canvas 合成、预览和保存到相册。
4. 用户保存图片后自行发送给好友或朋友圈。产品不伪装成直接分享成功，也不把保存图片描述成已经发出。
5. 两类海报都只包含品牌、公开角色资料、邀请文案和小程序码，不包含质量档位、用户材料、证据、分数或报告正文。

## 理由

- 在个人开发者可用的能力范围内保留真实、可验证的传播闭环。
- 总览海报让首页具备完整的产品介绍能力，单角色海报继续承接报告结束后的情绪钩子。
- 服务端固定小程序码目标，避免客户端构造任意页面或把私人报告内容写入场景参数。
- 相册保存由用户明确点击触发，权限失败有可恢复路径，也不会阻塞一次性评审的离场。

## 替代方案

- 继续依赖原生好友或朋友圈分享：主体能力不可用，入口会成为无法兑现的承诺。
- 分享报告截图或长图：传播信息更多，但会泄露材料、证据和分数，不采用。
- 使用普通二维码跳转网页：需要额外的公开 Web 落地页，也不能直接还原当前小程序角色入口。

## 影响

- [2026-07-17：评审保持一次性使用，分享承接传播](2026-07-17-one-shot-review-and-sharing.md) 中关于原生分享卡片和朋友圈单页的决定由本 ADR 取代；一次性评审和分享隐私边界继续有效。
- 云函数部署产物增加 `wx-server-sdk`，真机发布验收增加小程序码识别与相册权限检查。
- 分享指标区分海报生成、保存、扫码进入和进入后提交，不把“生成图片”误记为已经完成外部分享。
