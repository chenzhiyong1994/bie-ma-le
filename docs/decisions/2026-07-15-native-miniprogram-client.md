# 首个客户端切片使用原生微信小程序

日期：2026-07-15

状态：已采用

## 背景

仓库此前只有产品定义，没有运行时代码。第一个工程目标是尽快交付一个可以在微信开发者工具中运行、可由产品负责人完整体验的“简历终结者”模拟闭环。

当前切片只有一个角色、固定模拟数据和五个页面，不需要跨端复用、复杂状态管理或第三方组件生态。

## 决定

客户端首切片使用微信小程序原生 WXML、WXSS 和 JavaScript，不引入 Taro、uni-app、组件库或运行时依赖。

角色信息、脱敏样例、模拟分析阶段和结构化报告集中在 `apps/miniprogram/data/mock.js`，页面只负责输入、导航、状态展示和交互。

## 理由

1. 可以直接在微信开发者工具中导入运行，不需要安装依赖或执行构建。
2. 首切片的主要不确定性是产品体验，不是跨端工程能力；原生实现能减少构建链和框架配置带来的干扰。
3. 小程序原生 API 足以覆盖表单、页面导航、模拟异步状态和报告交互。
4. 集中的模拟数据结构可以在下一切片替换为真实 API 响应，而不需要重做页面信息架构。

## 替代方案

- Taro 或 uni-app：适合明确需要多端发布或复用 React/Vue 生态的项目，但当前会增加依赖、构建和调试成本。
- WebView/H5：开发自由度高，但不能代表原生小程序的真实交互和发布环境。
- 先搭后端或 AI 服务：无法尽快验证用户从提交材料到阅读报告的完整体验，因此不符合当前纵向切片策略。

## 影响

- 当前小程序没有安装步骤和外部运行时依赖。
- 后续接入真实 AI 时，应保持页面消费的结构化报告字段稳定，将模拟数据源替换为 API 状态与响应。
- 如果未来确认需要多端发布，再基于实际复用收益评估迁移；本决策不提前承诺长期拒绝跨端框架。
